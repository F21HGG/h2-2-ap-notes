# 中国移动 H2-2 光猫改有线 AP：一次实机记录

这是一台 H2-2 光猫改作有线无线接入点（AP）的实机记录。上游路由器负责拨号、DHCP 和 DNS，H2-2 通过网线接入上游局域网，并提供 2.4 GHz 和 5 GHz Wi-Fi。

**这不是通用的一键安装教程。** 本文涉及厂商内部配置、内核私有接口和自启动组件。不同运营商定制版本、固件、端口映射或硬件可能不同。操作前请确认你拥有设备的管理权限，并保留独立的网络和设备恢复途径。

## 已验证范围

| 项目 | 本次设备及结果 |
| --- | --- |
| 设备 | 中国移动 H2-2，固件 `V1.3.3.00.04a`；具体行为以设备回读为准 |
| 上游 | 天翼网关作为主路由，通过网线连接 H2-2 的第三个网口 |
| 本机接口 | 上联 `eth2`；2.4 GHz `wlan0`；5 GHz `wlan4`。换端口或换固件时必须重新核实 |
| 测试结果 | H2 重启后，两个 Wi-Fi 都能通过 DHCP 连接；手机关闭移动数据后能打开百度和 B 站 |
| 后续回读 | 重启后开机组件自动解除三处过滤；约 3 小时 49 分钟后回读仍为解除状态 |
| 未确认 | 手机当时报告的 `192.168.1.1` 更可能是网关，不能据此认定为手机自身 IPv4 地址 |

IPv6 没有作为成功验收项：后续测试中，手机直连天翼 Wi-Fi 和连接 H2 5 GHz 时，都无法打开中科大 IPv6 专用测速页面。H2 和上游同时使用 `fe80::1`，这是需要排查的地址重复，但尚未证明它是故障原因。

## 主要问题和处理

1. **避免两个 DHCP 服务竞争。** 本机关闭了 H2 的 IPv4 DHCP 服务、DHCP 中继及相关地址池，也关闭了本机 DHCPv6 服务及地址池；客户端由上游路由器分配地址。该固件的 RA 设置没有直接的总开关，曾将路由通告的路由器生命周期和 DHCPv6 相关标志设为 0。其他固件的表结构和字段可能不同，不要直接照搬数据库行号。
2. **关闭异常 DNS 强制应答。** 在问题出现时，即使显式查询公共 DNS，UDP 查询仍被应答为 H2 的管理地址，而相同查询通过 TCP 得到正常结果。仅把 `DNSPlcCfg.DpiDNSSwitch` 设为 `0` 并不足以确保运行时关闭；本机还将 `PDTCTUSERINFO[0].tForcePushFlg` 设为 `0` 并保存。重启后 `/var/deceive.conf` 的 `Enable` 回读为 `0`。应在设备上分别检查 UDP、TCP 和重启后的实际行为。
3. **解除阻断 DHCP 的桥接过滤。** 本机的 `eth2`、`wlan0` 和 `wlan4` 均存在 `Ifwd.Type:[1], Ifwd.Protocol:[10]` 的目标过滤规则。仅解除其中一处并未解决问题；三处均解除后，两个频段的客户端获得了上游 DHCP。此处 `10` 是设备显示的值，不应推断其他固件使用相同表示或行为。
4. **应对开机时规则重建。** 原厂管理程序会重新施加过滤规则。本机新增一个受限的本地 helper 和 Felix OSGi 组件；组件每 15 秒检查三个指定接口，helper 只在匹配已验证规则时执行解除，不周期性写入闪存。重启后实测该组合仍能工作。

需要区分厂商管理器显示的规则和内核运行状态：管理器可能仍显示原规则。对本机来说，应回读 `/proc/net/brport`，再用实际设备申请新租约和访问网站验证。

## 只读检查

登录已获得授权的 H2 命令行后，先确认设备版本和接口；以下命令只读取状态：

```sh
cat /proc/zxic/softVersion
brctl show
brctl showmacs br0
cat /proc/net/brport
sidbg 1 brgrp_mgr show portfilter
sidbg 1 DB p DHCPSHostCfg
sidbg 1 DB p DHCP6SHostCfg
sidbg 1 DB p DNSPlcCfg
sidbg 1 DB p PDTCTUSERINFO
```

结合 `brctl showmacs br0`、接线变化和各接口的 bridge port 编号确认上联，而不是假设所有设备的第三口都是 `eth2`。如果上述文件、字段或命令不存在，停止套用本方案。

排查 DNS 时，可从客户端分别运行以下命令，并比较应答，而不要只看设置界面：

```sh
dig @223.5.5.5 www.baidu.com A +time=3 +tries=1
dig +tcp @223.5.5.5 www.baidu.com A +time=3 +tries=1
```

两次查询应在同一网络环境中进行。域名解析结果会随时间和地区变化；如果某一方式返回 H2 的私有管理地址，需要进一步确认是否被设备拦截，不能仅凭一个查询结果判定所有 DNS 故障。

## 自启动组件的复现线索

[`src/dhcp_filter.S`](src/dhcp_filter.S) 是本机使用的 ARM Linux helper 源码；[`src/build_worker_bundle.py`](src/build_worker_bundle.py) 生成 Java 5 兼容的 OSGi bundle。它们是供审阅和研究的源码，**不是可跨固件直接安装的成品**。

helper 只接受 `wlan0`、`wlan4`、`eth2`，以及 `0` 或 `1` 作为操作参数。参数 `1` 在 `/proc/net/brport` 中找到预期目标规则后，通过设备私有 bridge ioctl 请求解除；参数 `0` 请求恢复规则。OSGi 组件周期性执行三个接口的 `1` 操作。[实现与验证细节](IMPLEMENTATION.md)记录了本机的配置和恢复思路。

本机部署时使用 root 持有的 `/userconfig/h2-ap/filter`（setuid）和 `/userconfig/h2-ap/worker.jar`，在现有 Felix `felix.auto.start.1` 配置中增加该 bundle。目录、文件及其所有上级目录都必须防止不可信账号改写或替换。**setuid 程序扩大了本机可用权限：能够执行该 helper 的本地账号可以改变这三个接口的过滤状态。** 如果不可信账号能够替换组件或其路径，也可能造成更严重的权限问题。必须评估设备上的本地账号、路径权限及厂商安全策略，再决定是否接受这一取舍。

本机在变更前备份了原 Felix 配置到 `/userconfig/h2-ap/config.original`，通过隔离实例验证后才修改现有配置。生产环境中请保留设备特定的原始备份，不要复制本仓库之外其他设备的配置文件。Felix 可能缓存已安装的 bundle；仅删除自启动条目不一定停止已缓存的组件。恢复前应先停用 helper，再核验并恢复该设备自己的配置，重启后确认组件及过滤规则状态。DNS、DHCP、RA 的原始配置需要分别备份和恢复，Felix 配置备份不包含这些内容。

`sidbg 1 DB save` 会保存整个数据库，不只是当前字段。写入前应记录当前值、检查其他待保存改动，并准备恢复方法；写入后应回读运行值、持久化值并重启验证。不要仅凭命令返回成功就判断实际转发正常。

## 验收与注意事项

- 保留上游路由器的 Wi-Fi 或其他独立管理通道。确认光猫第三网口的上联不会因操作失联。
- 分别让 2.4 GHz 和 5 GHz 客户端重新获取 DHCP 租约，核对客户端 IPv4、掩码、网关和 DNS；网关应是上游路由器，而不是 H2 原管理地址。
- 暂时关闭手机移动数据，实际打开网页；再重启 H2，等待其自启动组件加载后重复测试。刚开机时 DHCP 可能暂不可用。
- H2 原管理地址位于独立子网时，上游子网的手机不一定能直接访问。一次临时新增同网段地址的尝试能响应 ping，但网页连接超时；该方案尚未完成，不要以为已经提供了通用管理地址。
- Wi-Fi 改名或改密码通常不改变桥接口名，但如果切换了 SSID、接口映射、网口或固件，就必须重新核对过滤规则和两个频段的端到端表现。
- Telnet 和厂商调试接口可能暴露高权限，应仅在可信的局域网内使用。不要公开设备背面标签、密码、序列号、配置备份或原始日志。

本记录来自单台设备和有限时间的验证，不保证其他版本适用，也不能证明长期稳定性。
